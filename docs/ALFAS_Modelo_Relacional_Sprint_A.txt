ALFAS — MODELO RELACIONAL DE DADOS | SPRINT A
Base documental: diagrama Data Relational Model v1.0 fornecido pelo professor; modelo de domínio, requisitos funcionais e Issue #3 do repositório ALFAS.
Os tipos são lógicos/genéricos e devem ser adaptados ao SGBD escolhido (MySQL ou SQL Server).
PK = chave primária | FK = chave estrangeira | UK = único.

1. UTILIZADORES E ACESSO

GENDERS
- id INT PK
- gender VARCHAR(50) NOT NULL

ROLES
- id INT PK
- name VARCHAR(50) NOT NULL UK

ROLE_USER
- role_id INT PK, FK -> ROLES.id
- user_id INT PK, FK -> USERS.id
- PK composta (role_id, user_id)

USERS
- id INT PK
- name VARCHAR(150) NOT NULL
- gender_id INT FK -> GENDERS.id
- schoolyear_id INT FK -> SCHOOLYEARS.id
- birth_date DATE
- parental_consent BOOLEAN NOT NULL DEFAULT FALSE
- email VARCHAR(254) NOT NULL UK
- img_url VARCHAR(500)
- email_verified_at DATETIME
- password VARCHAR(255) NOT NULL
- remember_token VARCHAR(255)
- userstate_id INT FK -> USERSTATES.id

USERSTATES
- id INT PK
- state VARCHAR(50) NOT NULL

SCHOOLYEARS
- id INT PK
- schoolyear VARCHAR(50) NOT NULL

- QUIZTYPES 1:N QUIZZES

- QUIZZES 1:N QUESTIONS

7. REGRAS DE NEGÓCIO E INTEGRIDADE

- Menores necessitam de consentimento parental antes da ativação/acesso (RF02 e modelo de domínio).
- O diagrama guarda parental_consent em USERS. Não foi criada tabela autónoma de consentimentos porque a documentação consultada não especifica os dados do encarregado de educação nem o histórico do consentimento.
- O acesso aos níveis do recurso e ao questionário final depende da conclusão do diagnóstico inicial (regra do modelo de domínio).
- Badge/certificado só é atribuído quando a nota do questionário final é >= 85% (regra do domínio e RF13).
- As respostas ficam ligadas à tentativa, pergunta e opção selecionada.
- Password deve ser guardada como hash, nunca em texto simples.
- FKs devem impedir registos órfãos; campos obrigatórios devem ser NOT NULL.
- Aplicar UNIQUE nas tabelas associativas para impedir relações duplicadas.

8. NORMALIZAÇÃO ATÉ 3FN

1FN: atributos atómicos; listas de papéis, respostas, recursos ou badges não são guardadas numa única coluna.
2FN: nas tabelas com PK composta, atributos não-chave dependem da chave completa. ROLE_USER contém apenas as duas FKs da PK.
3FN: géneros, papéis, estados, anos escolares e tipos têm tabelas próprias. Os atributos não-chave dependem da PK e não de outros atributos não-chave. USERS guarda FKs, não descrições repetidas desses elementos.

9. PONTOS A VALIDAR COM A EQUIPA/PROFESSOR

- O diagrama mostra QASTATES duas vezes; tratar como uma única tabela QASTATES, salvo indicação em contrário.
- Confirmar se cada pergunta permite apenas uma resposta. A UNIQUE(quiz_user_id, question_id) pressupõe uma resposta por pergunta.
- Confirmar se BADGES e CERTIFICATES são entidades separadas e se cada badge está associado a um recurso. São propostas para cumprir a parte de gamificação, não estão detalhadas no diagrama original.
- Confirmar o significado funcional de RESOURCE_USER e RESOURCELEVEL_USER (inscrição/favorito e progresso, respetivamente).
- Tipos e tamanhos são genéricos; adaptar BOOLEAN/BIT, DATETIME e geração de IDs ao SGBD escolhido.
